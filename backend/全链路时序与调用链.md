| 5 | `App.tsx:475` | 读到 `WAITING_ANSWER` 后调 `getCurrentQuestion` | → `api.ts:288` |

### 1.2 后端同步段（202 之前）

```
POST /api/interviews
  └─ interviews.create_interview          :387
       ├─ deps.get_db                    :~44    请求级 ORM 会话
       ├─ deps.get_visitor                       读 aiiv_user Cookie → sha256 → 查/建访客
       ├─ deps.require_same_origin                写方法做 Origin 校验（403 挡跨站）
       ├─ _read_upload                   :161    分块读，超 10MB 当场中断
       ├─ _quick_validate                :194    扩展名 / 大小 / 魔数
       ├─ _validate_question_count       :150    题数上限 30（防费用失控）
       ├─ sessions_repo.create           :432    建会话（status=PREPARING）
       ├─ _set_stage(db, session, "QUEUED")  :438
       ├─ _preparing.add(sid)            :447    ★ 进程内登记表
       └─ background_tasks.add_task(_run_preparation, ...)  :448
  ← 202 {session_id, status, state_version}
```

**关键节点作用**

| 节点 | 作用 | 为什么必须在这里 |
|---|---|---|
| `_read_upload:161` | 分块读取 + 超限中断 | 不把整个文件读进内存，也不让人用 100MB 拖死进程 |
| `_quick_validate:194` | 三重快速校验 | 在 202 之前给出结论，用户不用等后台跑完才知道文件是假的 |
| `_set_stage:210` | 写 `stage + stage_started_at` | 前端靠它显示"正在解析简历"并算耗时 |
| `_preparing:57` | 进程内"谁在跑"集合 | 只用于孤儿检测，不承担跨进程语义 |

### 1.3 后端异步段（进程内后台任务）

```
_run_preparation                          :296
  ├─ get_session_factory()()              自开 DB 会话（请求级已关闭）
  ├─ sessions_repo.get                    不是 PREPARING 就直接 return（幂等）
  ├─ _set_stage("VALIDATING_UPLOAD")
  ├─ build_parsed_input                   组装 ParsedInput（文件名/字节/JD文本）
  ├─ describe_input                       → 统计块数、字数，写进 progress
  ├─ _set_stage("PARSING_MATERIAL")
  ├─ parse_agent.parse_materials           ★ 视觉模型（qwen）
  ├─ _set_stage("VALIDATING_MATERIAL", warnings=n)
  ├─ materials_repo.save_parsed            ★ 材料落库（花钱的结果先存下来）
  ├─ _set_stage("GENERATING_QUESTIONS")
  ├─ question_agent.generate_questions     ★ 文本模型（deepseek）
  ├─ _set_stage("PERSISTING_QUESTIONS")
  └─ interview_workflow.start_interview    → 阶段一收尾
       ├─ questions_repo.insert_main_questions   :168
       ├─ graph.invoke(seed, thread_config)      :174  ★ 图第一次跑
       ├─ graph_runtime.interrupt_payload        :175  取当前题
       ├─ graph_runtime.snapshot_state           :179
       ├─ _next_question_payload                 :180  去 PG 补 question_id
       ├─ sessions_repo.begin_write              :184  ★ 取写入栅栏
       ├─ check_fence / touch                    :185-193
       └─ _bump_or_rollback → commit             :194-195
  finally: _preparing.discard + db.close         :373-375
  异常: _fail_preparation(db, sid, exc, stage)   :366-372
```

**`start_interview` 的参数含义**

| 参数 | 含义 |
|---|---|
| `db` | 后台任务自开的会话（不是请求级） |
| `graph` | `graph_runtime.get_compiled_graph()`，进程内缓存 |
| `session` | 已落库的会话行，`status` 必须是 `PREPARING` |
| `questions` | `QuestionSet`，准备阶段已生成，图里不再出题 |

**为什么要 `begin_write`**：启动也是一次会话写入。两个并发的"重试出题"如果都不占栅栏，能把同一场面试启动成两个不同题序。

### 1.4 阶段一的流转关系（一句话版）

```
前端点击 → createInterview → create_interview（同步校验 → 202）
                                    ↓ BackgroundTasks（脱离请求）
                            _run_preparation → 解析 → 出题 → start_interview
                                                              ↓
                                                    graph.invoke → wait_answer
                                                              ↓ interrupt 挂起
                                            前端轮询读到 WAITING_ANSWER → 拿第一题
```

## 2. 阶段二：一次回答提交（11 步）

### 2.1 完整调用链

```
POST /api/interviews/{id}/answers
  └─ interviews.submit_answer               :661
       ├─ deps.get_db / get_visitor / require_same_origin
       ├─ _owned_session                    :138   ← 会话归属（404 统一）
       ├─ interview_workflow.submit_answer  :213   ★ 业务真身
       │
       │  ① request_id 校验                    :238
       │  ② sessions_repo.get_owned           :241   SQL 里比身份
       │  ③ questions_repo.get + 归属比对      :243
       │  ④ idempotency.input_fingerprint     :247
       │     idempotency.classify_submission  :248
       │       ├─ conflict → RequestConflictError
       │       └─ replay   → _replay_response :820
       │  ⑤ sessions_repo.assert_can_answer   :259   ★ 必须在④之后
       │  ⑥ locks.acquire + start_auto_renew  :261
       │  ⑦ db.refresh + 再判幂等 + 比版本     :265-277
       │  ⑧ sessions_repo.begin_write         :282   ★ 取栅栏
       │  ⑨ _register_new_answer              :284 / :359
       │  ⑩ _run_and_persist                  :302 / :474
       │  ⑪ _finalize                          :737
       └─ finally: lock.release()             :316
```

### 2.2 逐步：位置 / 入参 / 做了什么 / 下一跳

| # | 步骤 | 位置 | 关键入参 | 做了什么 | 失败 → 错误码 |
|---|---|---|---|---|---|
| ① | id 合法性 | `:238` | `request_id` | 空或 >64 字符拒绝 | `REQUEST_CONFLICT` |
| ② | 归属校验 | `:241` → `sessions.py:74` | `session_id, owner_id, user_id` | SQL 里比对身份；不存在与无权限**合并 404** | `SESSION_NOT_FOUND` |
| ③ | 题目校验 | `:243` | `question_id` | 题目必须属于本会话 | `STALE_QUESTION` |
| ④ | 幂等判定 | `:247-256` → `idempotency.py:53` | `existing, input_hash, question_id` | 五态：proceed/conflict×2/replay/resume | `REQUEST_CONFLICT` |
| ⑤ | 终态检查 | `:259` → `sessions.py:122` | `session` | 终态拒绝 + 72h TTL 过期 | `SESSION_FINISHED` |
| ⑥ | 拿锁 | `:261` → `locks.py:161` | `session_id` | `SET key owner NX PX`，后台按 ttl/3 续期 | `LOCK_UNAVAILABLE` / `SESSION_BUSY` |
| ⑦ | 锁内重读 | `:265-277` | `expected_state_version` | 重新判幂等、比版本 | `VERSION_CONFLICT` |
| ⑧ | 取栅栏 | `:282` → `sessions.py:202` | `session` | 行锁内 `write_epoch += 1`，读出 `state_version`，**立刻提交** | `WriteFenceLostError` |
| ⑨ | 登记回答 | `:284` → `:359` | `request_id, input_hash, answer, skipped` | 短事务写 `PENDING`；唯一约束兜底 | `STALE_QUESTION` / `STATE_RECOVERY_REQUIRED` |
| ⑩ | 跑图 | `:302` → `:474` | `fence, is_retry, redis_client` | 先对账，再决定 resume / continue / 补写 | 见 2.3 |
| ⑪ | 收尾 | `:737` | `values, payload, rebuilt` | 落评分 → CAS → 快照 → 缓存 | `VERSION_CONFLICT` |

### 2.3 `_run_and_persist:474` 的四分支（最核心的一段）

```
snapshot(graph, session_id)                    :499   → GraphSnapshot
  │
  ├─ GRAPH_MISSING        → answers_repo.fail(STATE_RECOVERY_REQUIRED) + raise   :500-506
  ├─ _answer_position(db, sid, question)       :508   算出 index / completed_before
  ├─ mark_stage("GRAPH_RUNNING") + record_graph_position   :510-518  记下处理前位置
  │
  ├─ GRAPH_WAITING
  │    ├─ waits_for(...) == True  → resume_answer → _persist_success   :520-533
  │    ├─ waits_for(...) == False 且 is_retry → _rebuild_from_state（只补写） :535-546
  │    └─ 其它（首次提交却位置不符）→ fail + STATE_RECOVERY_REQUIRED   :548-554
  │
  ├─ GRAPH_NODE_FAILED    → continue_run → _persist_success   :556-567
  │
  └─ 图已跑完
       ├─ is_retry → _rebuild_from_state      :569-575
       └─ 否则     → fail + STATE_RECOVERY_REQUIRED   :577-582
```

### 2.4 `_finalize:737` 的固定顺序（不可调换）

```

```

### 2.5 阶段二流转关系（一句话版）

```
前端 submitAnswer（同 request_id）
   ↓
submit_answer（API）→ _owned_session → workflow.submit_answer
   ↓
归属 → 题目 → 幂等 → 终态 → 拿锁 → 重读 → 占栅栏 → 登记 PENDING
   ↓
```

## 4. 关键节点作用表

### 4.1 图里的 7 个节点

| 节点 | 位置 | 作用 | 不做什么（重要） |
|---|---|---|---|
| `prepare` | `nodes.py:44` | 归一化种子 state，复校验题目集 | **不解析、不出题**（准备阶段已做完） |
| `dispatch` | `:59` | 把第 N 道主问题装进 `pending_question`，记 `asked_contents` | 不调模型，纯推导，幂等 |
| `wait_answer` | `:116` | `interrupt()` 挂起，校验 resume 值 | **零副作用**：不写库、不调模型（会被重跑） |
| `evaluate_answer_node` | `:154` | 调评分模型；`skipped` 直接记 `None` | 失败**不吞**，直接抛（重试不产生重复评分） |
| `decide_followup_node` | `:169` | 规则链裁决是否追问 | 纯 Python，无模型调用 |
| `build_followup_node` | `:206` | 生成追问 | 失败降级而非中断（记 `followup_failures`） |
| `advance_node` | `:289` | 推进主问题序号或收尾 | 不判断"要不要继续"，那是条件边的事 |

### 4.2 非图的关键函数

| 函数 | 位置 | 作用 | 一句话记住 |
|---|---|---|---|
| `get_owned` | `sessions.py:74` | 归属校验 | 身份二选一，**绝不同时成立**；无权限与不存在都 404 |
| `assert_can_answer` | `:122` | 终态 + TTL | 终态与过期在这里拦，不进评分 |
| `begin_write` | `:202` | 取写入栅栏 | 行锁递增 `write_epoch` 后**立刻提交**，不带锁跑模型 |
| `bump_state_version` | `:242` | CAS 推进版本 | `WHERE state_version=? AND write_epoch=?`，rowcount=0 就拒 |
| `classify_submission` | `idempotency.py:53` | 幂等分类 | 同 id 不同内容 = conflict，才算"冲突" |
| `snapshot` | `graph_runtime.py:139` | 取图位置 | 值必须**一次取齐**，分两次取会互相矛盾 |
| `waits_for` | `:125` | 对账 | 返回 `True/False/None`，`None` ≠ `False` |
| `_answer_position` | `workflow.py:422` | 定位下标 | 不用 `evaluations[-1]`，图可能已推进 |
| `_run_and_persist` | `:474` | 对账分派 | **先对账，再决定跑不跑** |
| `_rebuild_from_state` | `:597` | 只补写 | 图已消费过这次回答，绝不重投 |
| `_finalize` | `:737` | 统一收尾 | 成功与补写共用一条路径，只差 `rebuilt` 标记 |
| `_fail_preparation` | `interviews.py:231` | 失败收口 | 绝不留永远 `PREPARING` 的僵尸 |

## 6. 三条链路的最小记忆版

```
① 准备：点上传 → 同步校验 202 → 后台解析 → 出题 → 入库 → 图启动停在第一题
② 答题：提交 → 认人认题认幂等 → 锁 → 栅栏 → 跑图评分追问 → CAS 落库 → 下一题
③ 补偿：Worker 扫表 → 条件抢占 → 拿锁 → 原始 request_id 续跑 → 同一条收尾路径
```
